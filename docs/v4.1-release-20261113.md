# CryptoBench-SC V4.1 公开材料补全记录（2026-11-13）

## 公开材料已完成

以学长最新交付的 `CryptoBench-SC-170-20261112-release.tar.gz` 为权威来源，重新导入了
`cryptobench-sc-v4@4.1.0` 的公开部分：

- 170 道公开题，题号 001–170 连续，套件仍为
  `CBSC-V4-COMPREHENSIVE-BLOCK-CIPHER-170-20260805`。
- 75 个公开附件全部非空，共约 9.2 MB（最小 326 字节，最大约 4.3 MB）。
- `catalog.json`、`public-tasks.zip` 和前端元数据已重新生成，哈希与 ZIP 内容一致。
- 旧版本 `cryptobench-sc-v4@4.0.0` 保持不变。
- `executionReady` 仍为 `false`，与材料覆盖保持一致。

相比上一版，`sourceCommit` 元数据不再错误引用网站仓库自身的 HEAD；导入器现在只在该
目录本身就是 Git 仓库根时记录提交号。

## 服务端评分仍然缺口的依据

新版包解决了公开输入，但它并没有把 001–105 题变成确定性的服务端评分器：

- 任务级验证器只有 65 个（对应 106–170 题），001–105 题没有 `oracle/validator.py`。
- 170 份 `hidden/oracle.json` 里，只有约 52 题有可直接机械判定的单一最终答案
  （标量或结构化值）；其余约 118 题的评分是语义评分、replay 校验或工作区解析。
- 上游 `oracle_policy` 明确说明多字段论文/表格题的数值节点“由 LLM 抽取器语义评分，
  而不是框架的单一数值匹配器”。`oracle_replay` 出现在 99 题中。

这带来一个架构性约束：本网站的执行模型是声明式最终答案校验（只比较
`artifact.answer`），而上游 CryptoBench-SC 的正式评分依赖沙箱工作区和逐题 Python
验证器。二者不能靠“补几个文件”等价替换。

因此，在获得 170 题的确定性最终答案规范、或把沙箱+验证器运行环境接入网站之前，
`executionReady` 应保持 `false`。

## 服务端评分器骨架（2026-11-13 实施）

为后续任一路径铺路，本仓库现在包含：

- `CryptobenchV4Evaluator`：V4.1 的服务端评分器，支持 numeric（容差）、string、
  one-of、boolean、exact-json 规则；`dynamic` 规则一律按未通过处理（fail-closed）。
- `scripts/build_v4_evaluator_catalog.py`：从 staged release 的 170 份 oracle 里，
  只提取无歧义的确定性最终答案，其余标为 `dynamic`。
- 私有目录 `evaluation/cryptobench-sc-v4/4.1.0/tasks.json`：170 题的私有评分目录，
  不进入静态资源。

当前提取结果：170 题中 44 题有无歧义的确定性最终答案（12 numeric、31 string、
1 boolean），其余 126 题标为 `dynamic`。生成器只接受 oracle 中明确命名的
`primary_answer`/`primary_numeric_answer`/`active_sbox_count`/`reachable`/
`probability_approx` 字段；`hard_task_oracle_v1` 的多字段、replay、语义评分答案
一律标 `dynamic`，避免像此前把某个中间聚合值误当作最终答案。评分器对 `2^-41`、
`2^(-41)`、`2^{-41}`、`1/2^41` 这类等价概率写法做了数值归一，因此 31 个 string
概率题是稳健的。`executionReady` 保持 `false`。
